🤔 So what actually IS immutable?

It means /usr is read-only. You can't sudo rm -rf /usr (yes, we've all been there). You can't install a broken AUR package that takes down your desktop. You can't accumulate five years of orphaned configs that make your system crawl. The OS is locked. Period.

When you need an app: run it in a container. Your Python experiments stay in their box. Your weird npm packages stay in their box. Your "let me try this random binary from GitHub" stays in its box. When the system updates: it downloads a whole new image and swaps to it. If it fails, it rolls back. You don't fix your OS — your OS fixes itself.

Same AcreetionOS you know. Same Arch under the hood. Same AUR. Same Cinnamon. Just locked down so your curiosity doesn't cost you your homework.

🔄 Recovery System — You Can't Permanently Break It

Even if you somehow manage to corrupt the base system, AcreetionOS Immutable has your back. The recovery system automatically detects boot failures and offers to restore the immutable base — while keeping all your files and containers intact.

🆘 Recovery Mode

A dedicated boot entry in systemd-boot. Select it at startup and the system reinstalls the immutable base from a known-good image. Your /home is untouched.

❤️‍🩹 Boot Health Check

systemd service monitors every boot. If the system fails to start 3 times in a row, recovery mode is offered automatically. No manual intervention needed.

🛠️ immutable-recover

CLI tool that pulls a fresh immutable base image from Cloudflare R2 and reinstalls the core OS — preserving /home, containers, and overlay configs. Run it from the recovery shell.

📦 immutable-update

Atomic A/B update mechanism. The current system is slot A. Updates download to slot B. Reboot into B. If it fails, reboot back to A. No partial upgrades, no broken states.

Your documents, downloads, application containers, and /home are stored on separate overlays and are never touched during recovery or updates. Only the immutable base (/usr, /bin, /lib) gets replaced.
